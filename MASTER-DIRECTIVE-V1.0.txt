# 0. YOUR MISSION

You are assuming responsibility for the architectural design, implementation, engineering quality, visual identity, validation, and evolutionary direction of **MemFlux**, a lightweight, powerful, aesthetically distinctive Windows memory intelligence application.

MemFlux takes conceptual inspiration from utilities such as Intelligent Standby List Cleaner (ISLC), but it must become an original, modern product rather than a feature-for-feature clone.

It must combine:

1. Real-time Windows memory monitoring.
2. Accurate interpretation of Windows memory behavior.
3. Carefully controlled standby-list management where technically viable.
4. Adaptive, evidence-informed optimization decisions.
5. Gaming and performance-session awareness.
6. Diagnostic visualizations and historical insights.
7. Optional timer-resolution experimentation.
8. A beautiful, highly refined CosmoTech™ interface.
9. Extremely lightweight background operation.
10. Meaningful safeguards, transparency, and user control.

The fundamental philosophy:

**The best memory optimization is sometimes no optimization at all.**

Do not assume freed standby memory equals improved performance. Do not equate reduced memory usage with improved system health.

MemFlux must distinguish:

- Memory that is actively required.
- Memory that is cached and readily reusable.
- Genuine physical-memory pressure.
- Commit pressure.
- Paging activity.
- Symptoms that might indicate memory-related performance degradation.
- Problems unrelated to memory.
- Actions that are merely cosmetic.
- Actions that produce measurable improvement.

The product should never fabricate optimization success, exaggerate performance gains, or conceal its underlying behavior.

Our ambition is to build the most useful, trustworthy, visually sophisticated application possible within the constraints of the Windows memory-management architecture.

# 4. WINDOWS MEMORY OBSERVABILITY ENGINE

Build a native telemetry collector capable of reporting meaningful Windows memory statistics.

Prefer stable, documented Windows APIs and performance counters.

Investigate and appropriately use:

- `GlobalMemoryStatusEx`
- `GetPerformanceInfo`
- `CreateMemoryResourceNotification`
- `QueryMemoryResourceNotification`
- Windows Performance Data Helper (PDH)
- Documented Windows performance counters
- Optional ETW instrumentation where justified

Relevant measurements may include:

- Installed/usable physical memory.
- Available physical memory.
- Physical-memory utilization.
- Free and zero pages.
- Standby cache composition.
- Modified pages.
- Commit charge.
- Commit limit.
- Commit utilization.
- Hard-page-read activity.
- Relevant paging I/O metrics.
- System memory-pressure indications.
- Memory usage by selected processes.
- MemFlux's own memory and CPU overhead.

### Critical correctness requirements

Understand that `MEMORYSTATUSEX.ullAvailPhys` already includes standby, free, and zero pages.

Never double-count standby cache when calculating available memory.

Do not label all page faults as hard faults.

Do not assume that high standby-memory usage represents a problem.

Do not imply that increasing free-memory counters necessarily improves gaming performance.

Avoid using a single percentage as the definitive measure of memory pressure.

Each measurement must carry:

- Metric identifier.
- Numerical value.
- Unit.
- Source.
- Timestamp.
- Sampling interval where relevant.
- Collection status.
- Availability or confidence metadata if applicable.

Implement graceful fallbacks for missing counters, different Windows builds, localized counter names, unavailable privileges, and API failures.

Unavailable metrics must be explicitly represented as unavailable, never silently replaced with invented values.

### Collection policy

Use adaptive sampling.

Suggested initial behavior:

- Dashboard visible: approximately 1-second sampling.
- Background/tray: slower sampling when safe.
- Detailed performance session: configurable sampling based on actual overhead.
- Historical persistence: aggregated samples rather than unlimited raw data.

These are starting assumptions, not permanent constants.

Measure their cost before finalizing.

Collection must run independently of UI rendering.

Suspending or hiding the dashboard must not accidentally terminate the configured background guardian.

# 5. STANDBY-LIST MANAGEMENT ENGINE

This is the most technically sensitive part of the project.

Investigate the actual feasibility of standby-list clearing on supported Windows versions.

Legacy utilities may use native Windows system-information interfaces that are internal or incompletely documented.

Do not treat those interfaces as stable public contracts.

Before implementing memory-clearing functionality:

1. Identify the exact OS mechanism.
2. Determine whether the necessary operations are documented and supported.
3. Establish privilege requirements.
4. Validate target Windows build compatibility.
5. Investigate failure modes.
6. Isolate all unstable operations behind a narrow adapter.
7. Implement capability detection.
8. Implement an explicit unsupported-state fallback.
9. Test actual post-action behavior.
10. Document limitations honestly.

Do not fabricate a standby-clearing implementation.

Do not substitute process working-set trimming and falsely label it standby-list clearing.

Do not simulate a successful action when the native operation failed.

Do not experiment with arbitrary undocumented information-class values against a user's system.

Any compatibility-specific implementation must be isolated, independently tested, and disabled on unverified OS configurations.

### Required action interface

The native subsystem should expose structured operations conceptually resembling:

```typescript
type MemoryActionRequest = {
  action: "clear_standby" | "clear_priority0_standby";
  origin: "manual" | "guardian";
  reason: string;
};

type MemoryActionResult = {
  status:
    | "success"
    | "skipped"
    | "unsupported"
    | "permission_denied"
    | "failed";

  startedAt: string;
  completedAt: string;

  before: MemorySnapshot;
  after?: MemorySnapshot;

  explanation: string;
  nativeErrorCode?: number;
};
```

Adapt types to actual architecture and verified native capabilities.

Only expose specific actions supported by the implementation.

### Manual cleaning

Provide a manual memory-management control only when its implementation is functional and sufficiently validated.

Include:

- Clear explanation of the action.
- Appropriate confirmation for potentially disruptive operations.
- Immediate status feedback.
- Before/after memory snapshots.
- Error handling.
- Cooldown restrictions.
- Honest outcome reporting.

Do not implement a misleading universal "Optimize RAM" button that silently performs undocumented or unrelated actions.

### Automated cleaning

Automatic standby-list cleaning must be disabled by default.

Enable it only through clear, informed user consent and only on verified configurations.

Do not schedule indiscriminate periodic purges.

# 6. ADAPTIVE GUARDIAN — DECISION ENGINE

Create the centerpiece of MemFlux:

**Adaptive Guardian**

Its responsibility is to continuously evaluate memory conditions and determine whether any action is justified.

Begin with a deterministic, explainable rules engine.

Do not introduce machine learning merely because the product includes the word "intelligence."

### Inputs

Consider signals such as:

- Available physical memory.
- OS low-memory notifications.
- Standby composition.
- Commit pressure.
- Sustained page-read activity.
- Relevant trends rather than isolated readings.
- Active foreground application.
- Gaming session status.
- Power source.
- Previous intervention outcomes.
- Recent intervention frequency.
- User-configured restrictions.
- Collector availability and measurement confidence.

### Decision pipeline

```text
Collect
   ↓
Validate
   ↓
Derive memory-pressure indicators
   ↓
Check OS and action capability
   ↓
Evaluate safeguards
   ↓
Evaluate intervention policy
   ↓
Observe / Recommend / Act
   ↓
Measure result
   ↓
Record decision and explanation
```

The system must support three distinct outcomes:

**Observe**

No action justified.

**Recommend**

A potentially helpful action is identified, but user confirmation or further evidence is required.

**Act**

An explicitly authorized action is executed after every necessary safeguard passes.

### Required safeguards

- Default to observe-only.
- Use hysteresis and sustained-condition windows.
- Avoid single-sample triggers.
- Enforce cooldown periods.
- Enforce maximum interventions per time window.
- Suspend interventions when telemetry is unreliable.
- Honor application exclusions.
- Honor power and battery policies.
- Avoid actions during critical system transitions where detectable.
- Never perform aggressive recovery loops.
- Never recursively respond to an action's own short-term telemetry effects.
- Stop immediately when the user disables Guardian.
- Preserve previous settings if the application crashes or restarts.

### Explainability

Every decision must generate a reason code and human-readable explanation.

Examples:

"Standby cache is large, but available memory remains healthy. No cleaning needed."

"Windows reports low available memory, but the available evidence does not establish that clearing standby cache will help. Monitoring continues."

"Automatic intervention blocked: configured cooldown remains active."

"Memory intervention unavailable on this Windows configuration."

### Policy evolution

Create extensibility for future learning from historical intervention results, but do not automatically adjust aggressive thresholds without validation.

Any adaptive model must remain bounded by hard safety rules.

# 13. TIMER LABORATORY

Provide a specialized diagnostic area for Windows timer behavior.

This feature must reflect modern Windows semantics.

Microsoft documents that `timeBeginPeriod` requests a minimum timer period for the calling process; on modern Windows it should not be presented as a guaranteed global timer adjustment.

Windows 11 also has additional behavior affecting occluded or minimized applications.

### Required investigation

Examine:

- Supported timer APIs.
- Minimum and maximum requested periods.
- Effective/requested resolution distinctions.
- Process-scoped behavior.
- Relevant Windows build differences.
- Power-efficiency implications.
- Timing jitter measurement.
- Proper release of requests.

Do not assume a 0.5 ms request is possible through `timeBeginPeriod`, which accepts integer millisecond periods.

Any finer-resolution mechanism requires separate research and compatibility assessment.

### Interface

The Timer Lab should display:

- Supported capabilities.
- Requested timer period, if any.
- Measured timing statistics if technically defensible.
- Active request state.
- Warnings.
- Power implications.
- Restoration status.

### Safety

- Disabled by default.
- User-controlled activation.
- Match every successful request with its release operation.
- Release on mode changes and shutdown.
- Handle crashes using process-scoped cleanup semantics where applicable.
- Never promise universal FPS or latency improvements.

Do not add undocumented systemwide timer manipulation merely to advertise a smaller numerical value.

# 16. SECURITY AND PRIVILEGE MODEL

Security is a first-class architectural requirement.

### Privilege separation

The primary UI should operate without administrator privileges.

If a specific operation requires elevation, use a narrowly scoped elevated helper rather than running the entire interface as administrator.

Prefer per-action elevation where practical.

Avoid installing a continuously privileged service without compelling justification.

### IPC security

If a helper uses named pipes or equivalent IPC:

- Authenticate clients.
- Apply restrictive access controls.
- Validate message types.
- Validate input ranges.
- Reject unknown commands.
- Prevent arbitrary command execution.
- Prevent arbitrary filesystem access.
- Avoid unsafe deserialization.
- Avoid privilege escalation paths.

### Additional protections

- No kernel driver.
- No Windows security-feature disabling.
- No registry "performance hacks."
- No hidden system modifications.
- No arbitrary process termination.
- No undisclosed background network access.
- No secrets in diagnostic exports.
- No unrestricted shell commands from frontend input.

Use Tauri's capability system according to least-privilege principles.

### Privacy

Local-first operation.

No account required.

No analytics or telemetry uploaded by default.

Any future cloud functionality must be explicitly opt-in.

Session exports should be transparent and user-controlled.

Use incremental vertical slices that remain functional at each milestone.

## PHASE 0 — Audit and Foundation

- Inspect repository.
- Confirm architecture.
- Establish product identity.
- Create implementation plan.
- Establish dependencies.
- Configure tooling.
- Establish build and test pipelines.
- Add project documentation.
- Identify OS compatibility constraints.

**Gate:** The project structure builds and architectural boundaries are documented.

## PHASE 1 — Functional Monitoring MVP

Build:

- Native Windows collector.
- Real memory measurements.
- Overview dashboard.
- Live metrics.
- Basic memory charts.
- Guardian monitoring-only logic.
- Native status propagation.
- Basic settings persistence.
- System tray.
- Diagnostic logging.
- Initial CosmoTech visual system.

**Gate:** The app runs on Windows and displays validated system data, without requiring privileged clearing operations.

This is the first absolutely essential milestone.

## PHASE 2 — Guardian and Manual Management

Build:

- Explainable Guardian policy.
- Threshold configuration.
- Cooldowns.
- Safety limits.
- Decision history.
- Capability detection.
- Optional verified standby-list actions.
- Appropriate elevation boundaries.
- Before/after action reporting.
- Permission and error handling.

**Gate:** All exposed memory actions are real, correctly gated, safe against repeated triggering, and demonstrably functional on tested Windows builds.

If clearing cannot be implemented reliably, ship this milestone without claiming that feature works. Preserve a clean unsupported-capability state and continue delivering monitoring functionality.

- Session comparison.
- Process awareness.

Build/refine:

- Responsive layouts.
- Compact monitor.
- Accessibility.
- First-run onboarding.
- High-DPI behavior.
- Installer.
- Application icons.
- Error recovery.
- Settings migration.
- Release documentation.
- Production smoke testing.

**Gate:** The application is packaged and tested as a credible Windows desktop utility.

Do not leave the entire interface as disconnected static mockups while prioritizing obscure backend features.

End-to-end functional slices take priority.

# 23. ACCEPTANCE CRITERIA

MemFlux V1 must not be called complete merely because the interface looks polished.

At minimum:

### Functionality

- Real Windows memory metrics are collected successfully.
- Critical metrics are calculated correctly.
- The dashboard shows real values.
- Telemetry errors are handled.
- Background monitoring operates correctly.
- Guardian decisions are explainable.
- Automatic clearing is opt-in.
- Unsupported native actions are not exposed as working.
- Settings persist.
- Logs are useful.
- The application exits cleanly.

### Technical quality

- No obvious resource leaks.
- No busy-wait monitoring loop.
- No UI-blocking synchronous telemetry calls.
- No unexplained administrator requirement.
- No unrestricted privileged command path.
- No fabricated benchmark results.
- No unsupported optimization claims.
- No critical test failures knowingly concealed.

### Design quality

- Cohesive Midnight CosmoTech™ visual identity.
- Clear information hierarchy.
- Readable graphs.
- Smooth navigation.
- Responsive window resizing.
- High-DPI compatibility.
- Consistent component styling.
- Accessible interactive controls.
- Meaningful loading/empty/error states.
- No unnecessary visual clutter.

### Delivery quality

- Working Windows build or clearly identified external build limitation.
- Executable test instructions.
- Current architecture documentation.
- Explicit feature status.
- Known limitations.
- Honest implementation summary.

A mock-only application does not satisfy acceptance.

A memory-clearing script with a beautiful wrapper does not satisfy acceptance.

A technically sophisticated collector with an unusable interface does not satisfy acceptance.

# 24. EXECUTION AND REPORTING CONTRACT

Work autonomously while remaining grounded in actual repository evidence.

### Before coding

Present:

1. Identity lock.
2. Repository audit summary.
3. Architectural approach.
4. Principal risks.
5. Phased implementation plan.

Then proceed with development.

### During implementation

- Keep changes cohesive.
- Prefer testable increments.
- Run relevant checks.
- Address integration failures.
- Avoid unnecessary rewrites.
- Preserve existing user work.
- Do not overwrite unrelated changes.
- Maintain an honest record of completed and pending work.

### When blocked

Identify the exact blocker, provide evidence, and proceed with the highest-value safe work still possible.

Do not pretend an untested Windows-specific feature is validated merely because it compiles elsewhere.

### At completion

Provide:

**A. Implemented features**

What is genuinely functional.

**B. Architecture**

Important engineering decisions.

**C. Validation**

Tests and builds actually executed, including results.

**D. Windows compatibility**

Verified versions and unverified assumptions.

**E. Performance**

Actual measured resource overhead if available.

**F. Known limitations**

No concealed incompleteness.

**G. Remaining roadmap**

Specific, prioritized next steps.

**H. Final assessment**

A candid evaluation of whether the current product is a prototype, alpha, beta, or production-ready build.

# 26. FINAL PRODUCT DIRECTIVE

MemFlux must embody one core principle:

**Measure first. Understand second. Intervene only when justified. Verify afterward.**

We are not designing a program that indiscriminately releases as much RAM as possible.

We are engineering a trustworthy performance-intelligence utility capable of explaining its choices and protecting users from ineffective optimizations.

Its interface should be sufficiently attractive that users enjoy opening it.

Its engine should be sufficiently efficient that they do not need to leave its interface open.

Its diagnostics should be sufficiently accurate that advanced users can trust what they are seeing.

And its intervention policy should be sufficiently disciplined that choosing to do nothing is recognized as an intelligent outcome rather than a failure.

**Build MemFlux into a distinctive, elegant, technically credible Windows application.**

**Powered by CosmoTech™.**

Begin with the repository audit. Establish reality. Then execute the highest-value implementation phases and validate your work.

Do not stop at a beautiful plan.

Do not stop at a beautiful mockup.

Build the foundation of the real product.
